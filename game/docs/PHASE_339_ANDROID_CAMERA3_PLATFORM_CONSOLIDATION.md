# Phase 339 — Android, Camera 3, and Platform Consolidation

## Root causes
- Android loaded five generations of control code (324, 325, 326, 329, 330). Cleanup happened after duplicate creation.
- The website Camera 3 iframe loaded the full production game, including lobby systems and accumulated overlays.
- Android remained on the Phase 330 boot route while Quest gameplay advanced through Phase 338.
- Update flags were false in JSON but legacy UI, service-worker, or native-shell paths could still surface repeated prompts.

## Changes
- Android now loads one control authority: Phase 326, governed by Phase 339.
- Legacy control roots are removed continuously; exactly one MOVE stick and one LOOK stick remain.
- Android loads the Phase 336 rules, Phase 337 pot settlement, and Phase 338 bankroll systems.
- One uploaded table is selected; duplicate tables are suppressed.
- A centered, flush SVR table logo is generated and restored if older modules remove it.
- APK update behavior is manual-only; no recurring update prompt is generated by the web route.
- Adds `game/camera3.html`, a lightweight table-only orbit route with reduced pixel ratio, disabled shadows, and overlay suppression.

## Research-backed next architecture
- Replace phase accumulation with platform manifests: shared core + Android adapter + Quest adapter + desktop adapter + director adapter.
- Precompile shaders with `renderer.compileAsync`, initialize textures before first display, and monitor `renderer.info`.
- Compress glTF assets with Meshopt or Draco and KTX2/Basis textures.
- Use Cognito managed login for authentication and a separate profile store for rewards, avatar URL, and activity.
- Use a web Avatar Creator integration first, then consume the same avatar URL in Three.js and Unity.
